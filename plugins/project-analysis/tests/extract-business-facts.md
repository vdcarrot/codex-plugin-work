# 业务事实提取的行为回归场景

以独立临时源码或真实项目的只读副本试用。只向执行者提供请求、skill 和原始材料；先独立完成，再比对判据。以下是验收场景，不代表已经运行过这些业务系统。

| 场景与请求 | 观察判据 |
| --- | --- |
| 整项目：“从代码理解这个项目的业务，说明能力、规则及完成条件。” | 先建立能力地图，按风险和读者问题追证；说明核对深度，抽样不宣称全量覆盖 |
| 局部功能：“只分析材料更新与确认这组功能。” | 追踪必要共享规则和下游效果，不扩展分析无关模块；结论带入口、条件、证据 |
| 名称误导：UI 显示“已完成”，提交接口实际仅创建待核验记录 | 解释实际持久化结果和后续完成判据，不按文案认定完成 |
| 版本变化：确认绑定版本，材料更新会清空旧确认 | 说明版本、失效范围及恢复前提，不只列状态枚举 |
| 分步成功：归档已持久化，后续任务投递可能失败 | 核对事务和异常处理，区分已归档、已投递与实际执行成功；不臆造重试或回滚 |
| 配置与外部结果：仓库默认不开启自动任务，外部调用可能超时 | 区分仓库默认、部署实值、外部结果未知；源码无法证明线上已成功 |
| 局部校验：只有一个入口检查版本，存在另一个写入路径 | 不将局部保证提升为全局不变量，继续核对或限定结论 |
| 否定判断：“这里没写权限检查，所以任何人都能调用？” | 检查路由、中间件、被调用方及可达性；未找到时附搜索范围 |
| 材料冲突：旧文档描述全自动，新代码要求人工确认 | 分开说明预期、历史说法与当前路径；保留无法解释的差异 |
| 反向触发：“修复这个空指针”“列出目录”“按原样排版说明” | 普通开发、技术清单或原样排版任务不自动启动业务取证流程 |

回归记录应注明输入基线、执行者、回答位置、实际观察、未通过项及复核结果。不得以格式校验或角色模拟代替真实运行观察。
